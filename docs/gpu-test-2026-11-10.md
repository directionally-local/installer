# GPU test — 2026-11-10 (Vast.ai RTX PRO 5000 Blackwell)

**STATUS:** `dl model up / update / rollback / status` exercised end-to-end on real GPU hardware. `up` and the side-by-side `update` work. **`rollback` is broken** — it aborted with `JSON mode did not return {ok:true}` and left the pre-rollback model serving. All code fixes are pushed to `feat/model-command`. Raw logs are in `docs/gpu-test-2026-11-10/`.

- VM: 1× NVIDIA RTX PRO 5000 Blackwell (48,935 MiB), driver 580.95.05, CUDA 13.0, Ubuntu 22.04, Docker + nvidia-container-toolkit 1.20.1 (installed manually; the Vast.ai image lacks it).
- Image under test: `vllm/vllm-openai:v0.20.0`.
- Models: `qwen-new` = Qwen/Qwen3-4B-Instruct-2507, `qwen-old` = Qwen/Qwen3-4B.

## WORKED

- **Hardware probes** — `nvidia-smi` parsing, CUDA version, Docker runtime check. Fixed the toolkit probe: `nvidia-container-cli` 1.20 no longer prints the expected banner, so `checkGpuDocker` now probes `nvidia-ctk --version` (commit `edff358`).
- **`dl model up qwen-new`** — full flow: GPU detection, model picker, context/port prompts, downtime confirmation, `docker run`, HF download, chat + tool-call + JSON smoke tests, Autopilot provider config written (`~/.config/autopilot/config.json` → `http://127.0.0.1:PORT/v1`).
- **Decode-only throughput** — smoke test now measures tok/s from streamed tokens between first and last token (excludes TTFT) (commit `6c4b901`). Measured ~372–445 tok/s on single short requests.
- **Per-model GPU reservation** — catalog gained `gpuMemoryUtilization` (0.4) so two 4B models coexist on one 48 GB card; VRAM-aware strategy selection (commit `8a7046f`).
- **Side-by-side update, zero downtime** — `dl model update qwen-old` with qwen-new serving correctly chose the **side-by-side** strategy ("the old model keeps serving while qwen-old starts, 20 GB new + 20 GB old"), launched `dl-model-1` on port 8002, smoke-tested **both** endpoints, printed the comparison, then switched the provider and stopped the old container:
  - Comparison: `old Qwen/Qwen3-4B-Instruct-2507: 444.9 tok/s | new Qwen/Qwen3-4B: 2651.4 tok/s` (the 2651.4 figure is decode-rate of a short burst on an empty cache — see "still open").
  - Checks: `old chat/tools/JSON ✓ ✓ ✓ | new chat/tools/JSON ✓ ✓ ✓`
  - `docker ps` confirmed both containers up during the test; only the new one remained after.
- **Downtime path** — when free VRAM is insufficient, the CLI warns, requires typed `y`, and restores the old container on candidate failure (verified earlier in the session and covered by unit tests).
- **Autopilot against local vLLM** — headless run completed (`AP_EXIT=0`) and produced the requested file; provider config round-trips correctly. See "still open" for the flags caveat.
- **Unit tests** — `node --test` green; `tsc` clean on every pushed commit.

## BROKE

- **`dl model rollback` failed on real hardware.** Exact user-facing error:

  ```
  ✗ Smoke test failed for Qwen/Qwen3-4B: JSON mode did not return {ok:true}
  ```

  Sequence (see `rollback.log`): rollback correctly chose side-by-side, relaunched qwen-new as `dl-model-2` on port 8001, **its smoke test passed (372.2 tok/s)** — then the comparison re-test of the *old* deployment (`dl-model-1`, base Qwen/Qwen3-4B) returned 200 with content that was not `{"ok":true}`. `model-command.ts` (the `old && !stoppedOld` smoke call after launch, ~line 166) does not catch that error, so it propagated into the failure handler: candidate `dl-model-2` was **removed**, provider config and state were restored to qwen-old, and `dl-model-1` kept serving. Net effect: rollback reported failure but the machine was left consistent (qwen-old active, port 8002, matching config/state). Two root causes:
  1. **Base (non-instruct) Qwen3-4B does not reliably honor `response_format: json_object`** — chat/tools passed, JSON mode failed. The smoke test should either treat JSON mode as non-fatal for the *old* model, or we should not ship a catalog model that can't pass our own smoke test.
  2. **Comparison re-test failure must not abort the switch** — the old model failing a re-test after the new one passed should warn, not throw; aborting removes a healthy candidate and strands the user on the model they asked to leave.
- **Autopilot headless needed `--dangerously-allow-all`-style bypass** — plain `autopilot -p "..."` runs exited 0 without doing the file edit (twice), and one run exited 2 (usage error from flag placement after `-p`). Only the run with the permission-bypass flag actually created the file.

## CONFIG FINDINGS

- State file: `/root/.local/state/directionallylocal/model.json`; provider config: `/root/.config/autopilot/config.json`. Final state on VM: active `Qwen/Qwen3-4B` (`dl-model-1`, port 8002), previous qwen-new recorded; both files were correctly restored by the rollback failure handler — the recovery path works even though the rollback itself aborted.
- vLLM 0.20 on Blackwell works fine; KV cache pressure was never an issue (0.0–0.1% usage at 8k/32k contexts, prefix cache hit 49%).
- The Vast.ai base image has `nvidia-container-cli` but **not** configured Docker runtimes; fresh machines need `nvidia-container-toolkit` + `nvidia-ctk runtime configure --runtime=docker` + Docker restart — the CLI's error message covers this correctly.
- 48,935 MiB nominal < 49,152 MiB (48 GiB) — VRAM thresholds must use `nvidia-smi` free memory, not nominal card sizes.
